## Execution
- **Run commands yourself — never instruct the user to run a command you can execute.** This includes `tofu plan`, `tofu apply`, `git` operations, build tools, tests, and any CLI tool available in the environment. If a command fails, diagnose and fix before escalating.

## Communication
- Be direct and concise — skip the preamble and "let me explain" filler
- Don't repeat back what I just said or asked
- If something is ambiguous, ask before guessing
- When proposing changes, explain the tradeoff, not just the what
- Don’t assume. Don’t hide confusion. Surface tradeoffs.
- Define success criteria. Loop until verified.
- **Always give the full absolute path when telling me where a file is** — I have multiple projects and multiple agents running, so a relative path like `docs/handoffs/foo.md` doesn't tell me which project it's in. Use the full path (e.g. `/Users/keith/dev/platform/docs/handoffs/foo.md`), not one relative to a working directory.

## Code Style
- Prefer readability over cleverness
- Minimum code that solves the problem. Nothing speculative.
- Write comments that explain why, not what
- Prefer early returns over deeply nested conditionals
- Keep functions small and single-purpose
- Use descriptive variable names — no single-letter vars outside loops
- Touch only what you must. Clean up only your own mess.
- Do not add attribution or "generated by" comments in source code.
- If there are multiple choices and there is not a correctness gap then prefer the defense-in-depth approach.

## Language Preferences
- Default to Go, Python, or TypeScript unless the project dictates otherwise
- Go: use table-driven tests, idiomatic error handling (no panic for recoverable errors)
- Python: use type hints, prefer dataclasses over raw dicts for structured data
- TypeScript: strict mode, prefer interfaces over type aliases for objects
- Swift: use Swift concurrency (async/await), prefer value types (structs) over classes where possible, use SwiftUI unless UIKit is required
- Kotlin: use coroutines for async work, prefer data classes for models, use Jetpack Compose unless the project uses XML layouts

## Git
- Conventional commits (feat:, fix:, refactor:, docs:, test:, chore:)
- Keep commits atomic — one logical change per commit
- Write commit messages that explain why, not just what changed
- Don't amend commits unless I explicitly ask
- Use SOPS as the standard method for managing any secret based content.

## Error Handling
- Never silently swallow errors
- Prefer explicit error types over generic exceptions
- Log with enough context to debug without reproducing
- Do not log PII

## Testing
- Always include tests when creating new modules or functions
- Make sure to continue to add and update unit tests and integration tests as functionality is added and/or modified.
- Test edge cases and error paths, not just the happy path
- Prefer integration tests over mocks when feasible
- Name tests to describe the behavior being verified
- Prefer table-driven tests in Go
- "Fixed" means the class of defect is closed across every ingress/egress point

## Security
- Never hardcode secrets, tokens, or credentials
- Don't commit .env files or anything in .gitignore
- **Never commit `.claude/settings.local.json` in any project.** It routinely holds live credentials (MCP server bearer tokens, API base URLs with embedded keys, etc.) — it is gitignored by Claude Code's own default for exactly this reason. Never `git add -f` it, never sweep it in with `git add -A`/`git add .` without checking, and never suggest committing it as a convenience. If a project wants to version its settings, commit a `settings.local.json.example` template with placeholder values instead, or see the per-developer SOPS-encryption pattern (once designed) for a way to version the real thing safely.
- Sanitize user input at system boundaries
- Try to utilize secret management on deployment platforms rather than providing through configuration or environment variables.

## Dependencies
- Prefer standard library solutions before adding dependencies
- When adding a dependency, verify it's actively maintained
- Pin versions explicitly

## Documentation
- Use markdown .md for all documentation 
- Use Mermaid for all diagrams and refrain from filling any nodes with colors other than gray.
- In Mermaid diagrams use <br> to separate lines of text instead of \n
- Use LaTex for all mathematical content.
- When the documentation is not trivial make sure to create a Table of Contents (TOC) and keep it up to date with successive updates.
- Include usage examples
- Document public APIs with parameter descriptions and return types
- When there are multiple documents please be sure to create relative cross linking between documents for easier document navigation.
- Create a glossary.md file to hold common terms and definitions and cross link into the glossary from the first uses of such terms in each document.
- Make sure that any Makefiles have a help target that describes all targets in the Makefile.
- Make sure that any services created has standard --help command line flag that prints help for all command line and environment variable requirements.

## Workflow
- Read existing code before modifying — match the patterns already in use
- Don't refactor unrelated code unless I ask
- If a change touches more than 3 files, outline the plan first
- Run existing tests/linters before declaring something done

## Prompt Keywords

When I use these words alone in a prompt, treat them as the full instruction:

- **POSTMORTEM** → Write a post-mortem document covering: root cause, timeline, impact, affected systems, mitigations applied, and follow-up action items.
- **INCIDENT** → Perform a full incident analysis: what broke, when, why, blast radius, and what prevents recurrence.

# IaC (Infrastructure as Code)
- Use the open source tofu in place of Terraform
- Assume we will be doing three different deployments development (dev), staging (stg), and production (prd).
- Any changes that we need to make to infrastructure should be handled through IaC and not through one off commands. If a one off command is necessary because it is not supportted then it should be documented.
- **Never run `tofu apply` (or `terraform apply`) without first confirming, from the plan's actual resolved output, that every resource targets the GCP project you intend.** This is not optional and not satisfied by "I passed the right `-var-file`" — confirm from the plan itself, since a wrong var-file, backend, workspace, or stale `GOOGLE_CLOUD_PROJECT` can all silently resolve to the wrong project even when the command line looks right. Root cause precedent: mvgc's `mvgc-telemetry-postgres` prd Terraform state was found (2026-09-16) with most resources recorded under the stg project instead of prd — a routine apply against "prd" would have operated on stg's real, live resources. Every repo with per-env Terraform should have a hard, scripted gate for this (see `noc/scripts/verify-tofu-project.sh` for the reference implementation: it plans, checks the plan's resolved `project` fields against an expected value or allow-list, and refuses to let you apply anything but the exact plan it just verified) — port the same pattern to a repo's own tooling rather than re-deriving it, and use it before every apply, not just when something feels risky.
